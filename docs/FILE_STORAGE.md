# Зашифрованные вложения

Серверная поддержка общая для PDF, Word, изображений, голосовых сообщений и видеокружков. Файловая нода принимает непрозрачные бинарные блобы. Имя файла, MIME-тип, длительность, миниатюра и ключ расшифровки не передаются в открытые серверные метаданные.

## Ограничения

- На аккаунт: **5 ГиБ** (5 368 709 120 байт), включая активные загрузки. Вложения учитываются у отправителя; скачивание получателем не создаёт дополнительную копию в квоте.
- На одно зашифрованное вложение: **128 МиБ**. Размер включает тег шифрования.
- Хранение: **один календарный месяц после загрузки**, в UTC. 31 января → 28/29 февраля в то же время. Повторная выдача ссылки и повтор запроса загрузки срок не продлевают.
- Скачивание закрывается точно в `expires_at` (HTTP 410), независимо от очередного обхода очистки. Нода удаляет просроченные блобы при старте и затем раз в минуту. При ошибке диска удаление повторяется.
- Ссылка/сообщение в переписке остаётся. Клиент должен показывать «Срок хранения истёк» при 410. Базы и внешние резервные копии требуют своей политики хранения.

## API

Все `/api` запросы клиента требуют `Authorization: Bearer <session>`.

1. Клиент шифрует файл случайным AES-256-GCM ключом и случайным 12-байтовым nonce. SHA-256 считается **от шифротекста**, включая тег. Ключ остаётся на клиентах.
2. `POST /api/attachments` с `{room_id, size_bytes, sha256}` резервирует место. Доступ разрешён участнику текущего урока или подтверждённого личного диалога. Ответ: `attachment_id`, `upload_url`, `upload_token`, `reservation_until`, `retention_months`.
3. `PUT <upload_url>` с `Authorization: Bearer <upload_token>` и бинарным шифротекстом. Токен действителен 15 минут, связан с конкретной нодой, ID, размером и SHA-256. Нода потоково проверяет размер/хеш, сохраняет неизменяемый файл, сама подтверждает загрузку на управляющем сервере и возвращает `receipt`, `expires_at`.
4. `POST /api/attachments/:id/complete` с `{receipt}` — идемпотентное подтверждение со стороны владельца. Учёт занятого места уже выполняется по подтверждению ноды, поэтому обрыв клиента не скрывает файл из квоты. Нода повторяет неудачное подтверждение раз в минуту; просроченную непринятую загрузку удаляет.
5. В зашифрованное сообщение чата помещается описание вложения: ID, имя, тип, случайный файловый ключ, nonce, исходный размер; для войса/кружка — длительность и тип представления. Эти поля **не должны** передаваться незашифрованными в API хранения.
6. `GET /api/attachments/:id/download` проверяет список получателей и срок. Возвращает `download_url`, `download_token`, `expires_at`. Получатели фиксируются при загрузке; это участники чата на тот момент.
7. `GET <download_url>` с выданным Bearer-токеном возвращает `application/octet-stream`. Клиент расшифровывает файл локально. Нода повторно проверяет срок на диске, запрет не зависит от состояния управляющего процесса.

`GET /api/storage/usage` возвращает `used_bytes`, `reserved_bytes`, `available_bytes`, `quota_bytes`, `retention_months`, `max_file_bytes`. Истёкшие вложения не занимают пользовательскую квоту. Функция PostgreSQL блокирует квоту владельца на время резервирования; параллельные запросы и разные управляющие процессы не могут превысить 5 ГиБ.

Внутренний `POST /api/storage/committed` принимает только HMAC-подписанную квитанцию файловой ноды. Публичный клиент без серверного секрета не может выпустить такую квитанцию.

## Локальный запуск и ноды

Управляющий сервер — порт 4000, первая файловая нода `storage-local-1` — 4201. `start-cluster.ps1` запускает также локальную PostgreSQL, если присутствует установленный кластер, медиа-ноды, Web и собранный Windows-клиент. Скрипт повторного запуска пропускает занятые порты.

В `.env` (исключена из Git) должны быть `DATABASE_URL` и случайный `LIAPER_STORAGE_SECRET` длиной не менее 32 символов. Одинаковый секрет задаётся управляющему серверу и файловым нодам. В браузер и APK он не встраивается.

Переменные ноды: `FILE_NODE_ID`, `FILE_NODE_PORT`, `FILE_STORAGE_PATH` (по умолчанию `data/files`), `FILE_NODE_QUOTA_BYTES` (общая ёмкость ноды, по умолчанию 100 ГиБ), `CONTROL_URL`.

Управляющий сервер поддерживает `FILE_NODE_INTERNAL_URL`, `FILE_NODE_PUBLIC_URL` для одной ноды либо `FILE_NODES` — JSON-массив `{node_id, internal_url, public_url}`. При резервировании выбирается доступная по `/health` нода; объект остаётся привязанным к её ID. Все ноды из списка должны использовать общий секрет. Для Docker внутренняя нода задана как `http://liaper-files:4201`; публичный URL необходимо установить доступным клиентам адресом. Для HTTPS-приложения нужен HTTPS на файловом адресе.

## Готовность клиентов

В Web/Windows «Настройки → Хранилище» и Android «Профиль → Хранилище» показывают реальные серверные данные. Клиентские кнопки прикрепления, запись войсов/кружков и их воспроизведение ещё не подключены: текущий этап реализует серверный протокол и лимиты.

Перед подключением файловых ключей к чату нужно исправить отмеченный в `UX_UI_AUDIT.md` вывод старого ключа чата из публичного room_id. Хранилище само по себе не исправляет существующий обмен ключами и передачу медиа.

## Проверки

- `cargo test --workspace`: подписи, срок, потоковая проверка, выдача и удаление, доступ, квоты, роли контактов.
- С `LIAPER_TEST_DATABASE_URL`, указывающей на отдельную `liaper_test`, запускается проверка PostgreSQL: изоляция архивов, конфликты ревизий, перезапуск, одновременная резервация последнего места и одновременное принятие десятого ученика.
- `node tests/file-storage.integration.mjs` с той же тестовой БД запускает изолированные управляющий сервер и ноду: клиентское AES-шифрование → загрузка → автоматический учёт → скачивание другим участником → локальная расшифровка; постороннему доступ запрещён. Тестовые процессы и данные удаляются после проверки.
- `node --test clients/web-desktop/tests/lessonArchive.test.mjs` и `flutter test` проверяют общий формат зашифрованных архивов и конфликтную синхронизацию.
